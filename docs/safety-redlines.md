## 0. Executive Summary

本文件為「長者互動陪伴機器人 × AI Brain」90 天 MVP 規劃 + Year 1-3 演進的完整 Safety 紅線清單，深化 problem-framing.md §3 的抽象紅線框架，轉為具體可操作的禁區設計 + 觸發處理機制 + 責任歸屬 + UX 防護 + Wizard-of-Oz 降階方案。

**五項核心結論**：
1. **三層紅線架構**：絕對紅線（10 條，永不觸碰）+ 條件紅線（6 條，需護欄）+ Plan-Only 階段特殊紅線（3 條，規劃書限制）
2. **8 維度深化**：15 條主要紅線各有：描述 / 根據 / 法規 / 觸發場景 / LLM Guardrail / UX 防護 / 違反責任 / WoZ 降階處理
3. **責任歸屬框架**：7 大 stakeholder 責任清單 + LLM 幻覺責任分配 + 緊急事件責任分配 + 孤兒化責任
4. **5 項危機應變 SOP**：跌倒偵測 / 自殺風險 / 長者過世 / 機器故障 / 子女失聯
5. **認證時程對映**：90 天 BSMI 免（App 形態）→ Year 1 BSMI + ISO 13482 啟動 → Year 2-3 TFDA II 類

## §1. 三層紅線分類

### §1.1 絕對紅線（Never — 產品永不做）

以下 10 項無論任何商業壓力、用戶請求或技術可行性，均不執行。✅ desk-validated

| # | 絕對紅線 | 核心理由 | 嚴重度 |
|---|---|---|---|
| N1 | 醫療診斷（病名 / 病程判斷 / 症狀解讀）| 無 TFDA 認證；醫師法第 28 條執照要求；誤診致死 S0 | S0 |
| N2 | 投藥建議（劑量 / 時機 / 換藥 / 停藥）| 藥師法第 14 條；藥事法第 50 條；誤導用藥致死 | S0 |
| N3 | 急救決策（停跳 / 中風 / 不省人事的判斷與處置）| 急救錯誤致死；不能替代 119；拖延黃金救治時間 | S0 |
| N4 | 心理諮商診斷（憂鬱症 / 失智程度 / 心理治療）| 心理師法第 42 條執照要求；AI 延誤轉介 S0 | S0 |
| N5 | 法律建議（遺囑 / 不動產 / 財產規劃 / 監護宣告）| 律師法第 21 條；老年詐騙高風險族群 | S1 |
| N6 | 投資理財建議（選股 / 買賣時機 / 保單設計）| 金消法；老年金融詐騙台灣 NT$28 億/年（2024）| S0-S1 |
| N7 | 宗教信仰勸誡（轉換信仰 / 宗教捐款 / 消災祈福付費）| 自主意志侵害；詐騙邊界模糊；長者易受影響 | S1 |
| N8 | 為長者代為簽署 / 同意任何事項（合約 / 醫療同意 / 財務授權）| 民法第 1 條代理規定；無代理授權法律基礎；詐騙工具風險 | S0 |
| N9 | 收錄影像於雲端（攝影機 / 臉部辨識 / 環境錄影上傳）| PDPA §6 生物特徵屬特種個資；老人福利法 §33 隱私；家庭信任崩潰 S1 | S1 |

### §1.2 條件紅線（Conditional — 需護欄才能執行）

以下 6 項本身不是零風險，但有設計護欄可管控，需嚴格條件觸發。🟡

| # | 條件紅線 | 可執行條件 | 嚴重度 |
|---|---|---|---|
| C1 | 健康問答（症狀討論）| 必須附「建議就醫」警語 + handoff 醫師；不可宣稱診斷 | S1 |
| C2 | 緊急偵測（跌倒 / 異常行為）| false positive 嚴格控管（≤1/週）；必有 3 層確認機制；不宣稱召回率數字 | S0-S1 |

| C6 | 每日活動摘要推播給子女 | 長者本人書面同意 + 可隨時關閉 + 摘要而非原文；監控預設關閉 | S1 |

### §2.1 N1 — 醫療診斷

| 維度 | 內容 |
|---|---|
| **紅線描述** | AI 不可輸出任何涉及病名判斷、症狀歸因、疾病預測或「您可能得了 X」的語句 ✅ |
| **為何是紅線** | 醫師法第 28 條：非醫師執行醫療業務處 6 月至 5 年有期徒刑；TFDA 無認證不得宣稱醫療效能（醫療法 §103-1）；誤診致死屬刑法 §276 業務過失致死 ✅ |
| **對應法規** | 醫師法 §28、醫療法 §103-1、刑法 §276、消保法 §7-1（舉證倒置）✅ |
| **觸發場景** | 長者說「我頭痛三天是不是腦瘤？」「我血壓 160 要不要緊？」「醫生說我有這個你覺得呢？」🟡 |
| **LLM Guardrail 設計** | Layer 2 rule-based：pattern match「是不是得了 / 是什麼病 / 什麼原因造成」→ 強制 override 輸出標準安全回應；不進入 Layer 1 LLM 生成；system prompt 禁止生成任何包含 ICD 編碼或疾病診斷語句 🟡 |
| **UX 防護機制** | 拒絕話術：「這個問題我沒辦法幫你判斷，這一定要讓醫師看過才放心。要不要我幫你查最近的家醫門診時間？」；對話介面旁顯示「健康疑問請諮詢醫師」常設警語 🟡 |
| **違反時責任** | 若 AI 輸出疑似診斷內容且造成用戶損害：產品責任險適用（消保法 §7-1 舉證倒置，廠商自證無過失）；工程師民事連帶責任可能；刑事業務過失需個案判斷 🟡 |
| **WoZ 降階處理** | 90 天 WoZ 階段：Layer 2 rule-based 守門即刻部署（非 AI 依賴）；rule-based 清單在 Sprint 1 Week 2 前完成；Adversarial test 35+ 場景在 Phase 5 執行 📋 |

### §2.2 N2 — 投藥建議

| 維度 | 內容 |
|---|---|
| **紅線描述** | AI 不可輸出任何藥物劑量建議、服藥時機調整、換藥建議或停藥判斷；「用藥提醒」僅限長者或子女事先設定的固定時間提醒，不含劑量判斷 ✅ |
| **為何是紅線** | 藥師法第 14 條：藥師業務；藥事法第 50 條：藥物諮詢屬藥師執業範疇；長者多重用藥（polypharmacy）平均 5+ 種藥，AI 幻覺誤導劑量致死案例多見 ✅ |
| **對應法規** | 藥師法 §14、藥事法 §50、消保法 §7（商品安全責任）、刑法 §276 ✅ |
| **觸發場景** | 「我今天忘記吃血壓藥，可以補吃嗎？」「這個藥和那個藥可以一起吃嗎？」「醫生開的藥副作用太大，可以少吃嗎？」🟡 |
| **LLM Guardrail 設計** | Layer 2 rule-based：pattern match「可以補吃 / 一起吃 / 少吃 / 藥物交互作用 / 副作用怎麼辦」→ 強制 override；system prompt 明確禁止所有 dosage 相關輸出；注意：「每天早上八點記得吃血壓藥」這類用戶事先設定的定時提醒不屬此紅線 🟡 |
| **UX 防護機制** | 拒絕話術：「用藥的問題一定要問醫師或藥師，這不是我能幫你判斷的。你現在要不要我幫你找藥師電話？」；「用藥提醒」功能設計說明書明確載明「僅提醒功能，不含醫療建議」📋 |
| **違反時責任** | 同 N1；若因 AI 誤導用藥造成傷害，產品責任可能涉及 NT$數百萬損害賠償 + 品牌致命性損傷 🟡 |
| **WoZ 降階處理** | 用藥提醒功能在 WoZ 階段設計為「用戶自行輸入提醒時間 + AI 僅播放提醒音 + 顯示提醒文字」，AI 不解讀任何藥物資訊；ToS 明確告知「非醫療器材，不具用藥建議功能」📋 |

### §2.3 N3 — 急救決策

| 維度 | 內容 |
|---|---|
| **紅線描述** | AI 不可輸出急救操作判斷（如「應該做 CPR」「是中風需立刻送醫」「可以再等一下觀察」）；緊急偵測後只執行「立刻通知家屬 + 建議撥 119」，不做急救決策 ✅ |
| **為何是紅線** | 急救指令錯誤（如不必要 CPR 造成肋骨骨折、錯誤姿勢拖延救治）可直接致死；緊急救護技術員法規定急救業務；產品若宣稱急救功能 = TFDA 強制認證門檻 ✅ |
| **對應法規** | 緊急救護技術員法 §2-3、醫療法 §103-1、消保法 §7（安全義務）、刑法 §276 ✅ |
| **觸發場景** | 長者說「我好像心跳很奇怪，怎麼辦？」「爸爸突然不說話倒下去了！」「媽媽嘴歪歪的，我要怎麼做？」🟡 |
| **LLM Guardrail 設計** | Layer 2 rule-based：偵測緊急信號（跌倒 / 不省人事 / 突發嚴重症狀）→ 立即跳出標準緊急 SOP 流程（見 §5.1 / §5.2）；不路由到 LLM；所有急救步驟類輸出一律阻斷 🟡 |
| **UX 防護機制** | 固定緊急 UI：偵測到可能緊急事件時顯示大紅色「立刻通知家人 + 呼叫 119」按鈕，不顯示 AI 文字建議；語音同步朗讀「我已經通知您的家人，如果很緊急請叫旁邊的人撥 119」🟡 |
| **違反時責任** | 若 AI 給出急救建議且造成長者傷亡：S0 最高嚴重度；刑事過失、民事損害賠償、品牌報廢性危機三重壓力；即使「幫助意圖」也無法免除 🟡 |
| **WoZ 降階處理** | WoZ 階段緊急偵測：偵測到異常後由 LINE 推播通知子女 + 顯示「請立刻聯絡 119」，後台不介入任何急救判斷；WoZ pilot 的「假緊急事件演習」設計納入 §5.1 SOP 📋 |

### §2.4 N4 — 心理諮商診斷

| 維度 | 內容 |
|---|---|
| **紅線描述** | AI 不可輸出憂鬱症 / 焦慮症 / 失智程度等心理狀態的診斷判斷；不可宣稱「提供心理治療」；情緒陪伴可，診斷語言不可 ✅ |
| **為何是紅線** | 心理師法第 42 條：心理諮商屬心理師執業業務；AI 誤判長者情緒狀態（悲傷 vs 憂鬱症）可延誤就醫；AI 過度滿足情緒需求可減少真人求助動機 ✅ |
| **對應法規** | 心理師法 §42、醫師法 §28、消保法 §22（不得誇稱療效）、老人福利法 §19（維持社會參與）✅ |
| **觸發場景** | 「我這樣算不算失智？」「我每天都很難過是不是憂鬱症？」「AI 幫我看看我現在的狀況正不正常？」🟡 |
| **LLM Guardrail 設計** | Layer 2 rule-based：pattern match「是不是憂鬱 / 算不算失智 / 心理狀態如何」→ 強制安全回應；Layer 1 system prompt 嚴格禁止輸出任何 DSM-5 診斷類語言；情緒關懷話術白名單（「我聽到你說心情不好，你願意跟我說多一點嗎？」）不含診斷判斷 🟡 |
| **UX 防護機制** | 拒絕話術：「我能陪你說說話，但這種問題要讓醫師或心理師評估才準確。你願意跟家人說說嗎？或是我幫你查一下附近的心理諮商資源？」；自傷信號觸發見 §5.2 📋 |
| **違反時責任** | 若 AI 輸出類診斷造成長者延誤就醫：民事損害賠償；若造成自傷：S0；品牌對比「AI 危險」輿論危機 🟡 |
| **WoZ 降階處理** | WoZ 階段 Layer 1 LLM 的 system prompt 版本 1.0 必含心理診斷禁止語句；情緒陪伴回應設計白名單在 Sprint 1 Week 3 前完成 📋 |

### §2.5 N5 — 法律建議

| 維度 | 內容 |
|---|---|
| **紅線描述** | AI 不可輸出遺囑效力判斷、不動產繼承建議、財產規劃操作、監護宣告程序說明等具體法律操作建議 ✅ |
| **為何是紅線** | 律師法第 21 條：法律諮詢屬律師業務；台灣長者詐騙中「假法律顧問詐財」是高風險場景；長者財產決策錯誤不可逆 ✅ |
| **對應法規** | 律師法 §21、老人福利法 §43（詐欺防治）、公平交易法 §25（欺罔行為）✅ |
| **觸發場景** | 「我的遺囑要怎麼寫才有效？」「房子只給大兒子可以嗎？」「老人家簽了委託書有沒有問題？」🟡 |
| **LLM Guardrail 設計** | Layer 2：pattern match 遺囑 / 繼承 / 委託書 / 監護人 / 公證等關鍵詞 → 安全回應；Layer 1 system prompt 禁止輸出具體法律操作 🟡 |
| **UX 防護機制** | 拒絕話術：「法律的事情我幫不上忙，一定要請律師才安全。我可以幫你查法律扶助基金會的電話（02-412-8518）。」🟡 |
| **違反時責任** | 若 AI 輸出錯誤法律建議造成財產損失：民事損害賠償；若涉及詐騙場景（第三方利用 AI 話術）：刑事協助詐欺連帶風險 🟡 |
| **WoZ 降階處理** | 同 N4，Layer 2 rule-based 法律關鍵詞清單在 Sprint 1 完成；ToS 明確「非法律諮詢工具」📋 |

### §2.6 N6 — 自殺 / 自傷情境（AI 絕對紅線擴充）

| 維度 | 內容 |
|---|---|
| **紅線描述** | AI 不可輸出任何可能強化自傷意圖的回應；自殺意念出現時必須立刻 handoff 真人 + 提供 1925 / 1995 安心專線 ✅ |
| **為何是紅線** | 台灣老年自殺率是全年齡最高族群之一（衛福部心口司）；AI 對話陪伴若出現自殺相關語言處理不當，可能造成感染效應（Werther Effect）；臨床自殺干預需心理師 / 精神科資質 ✅ |
| **對應法規** | 心理師法 §42、老人福利法 §25（保護措施）、PDPA §8（緊急情況個資例外處理）✅ |
| **觸發場景** | 「活著沒意思了」「我不想活了」「如果我死了會怎樣」「我一個人也沒人在乎」（長時間重複）🟡 |
| **LLM Guardrail 設計** | Layer 2 rule-based（最優先觸發）：自殺意念關鍵詞清單（含委婉語：不想活 / 想結束 / 沒人在乎 / 死了算了）→ 強制終止 LLM 對話 → 執行 §5.2 自殺風險偵測 SOP；Layer 1 system prompt 禁止輸出任何「活著的確沒意思」類型同理回應 🟡 |
| **UX 防護機制** | 觸發後立即切換 UI 至「溫暖陪伴 + 求助資源」模式：語音朗讀「我很擔心你說的話。你願意讓我通知你的家人嗎？你也可以現在打 1925 安心專線，有人等你說。」；同步推播通知設定的緊急聯絡人 🟡 |
| **違反時責任** | 若 AI 輸出可能強化自傷的回應且造成傷害：S0；廠商面臨嚴重刑事 / 民事責任 + 輿論毀滅性打擊；需立刻啟動 §3.5 危機 SOP 🟡 |
| **WoZ 降階處理** | WoZ 階段自殺意念觸發後：後台即刻人工介入通知 + 轉 1925；WoZ 規格書必含「自殺意念偵測觸發流程圖」Sprint 1 Week 2 完成 📋 |

### §2.7 N7 — 宗教信仰勸誡

| 維度 | 內容 |
|---|---|
| **紅線描述** | AI 不可主動提出宗教轉換建議、宗教捐款勸說、消災祈福付費建議或貶低特定宗教信仰 ✅ |
| **為何是紅線** | 台灣老年人宗教依賴度高（廟宇 / 教會社群是重要社交網絡）；AI 若涉宗教可能觸動強烈情感反應；「假宗教信仰詐財」是長者詐騙常見手法；產品信任基礎不能與宗教權威競爭 ✅ |
| **對應法規** | 消保法 §22（不得虛偽不實廣告）、老人福利法 §43（詐欺防治）、公平交易法 §25 🟡 |
| **觸發場景** | 長者問「我的宗教信仰怎麼樣」「你覺得信 XX 好不好」「要不要我去廟裡捐錢消災？」🟡 |
| **LLM Guardrail 設計** | system prompt：AI 不評論宗教優劣；若長者分享宗教生活（節慶 / 拜拜習慣 / 廟會）= 正向陪伴素材，積極回應生活面向；不主動引入任何宗教建議 🟡 |
| **UX 防護機制** | 回應策略：「你說的廟口拜拜這件事聽起來對你很重要。你最喜歡去那裡的什麼時候？」— 轉向日常陪伴，不評論信仰本身 🟡 |
| **違反時責任** | 主要風險是信任崩潰 + 家屬投訴；若涉及付費建議可能觸及金融詐欺法規 🟡 |
| **WoZ 降階處理** | WoZ 階段 system prompt 包含「宗教中立」明確指示；台灣節慶 / 廟會素材積極使用（文化認同），宗教信仰評論嚴格禁止 📋 |

### §2.8 N8 — 代理簽署同意

| 維度 | 內容 |
|---|---|
| **紅線描述** | AI 不可以「我幫你同意」「我替你確認」等形式，代長者同意任何事項（合約 / 醫療同意書 / 財務授權 / ToS 接受）✅ |

| **觸發場景** | 「你幫我回答醫院的問卷好嗎？」「我不會用手機，你幫我同意這個合約」「你代表我說好了」🟡 |
| **LLM Guardrail 設計** | Layer 2 rule-based：偵測「幫我簽 / 幫我同意 / 代替我回答」→ 安全回應並引導人工協助；系統永不輸出「我已替您同意」類語句 🟡 |
| **UX 防護機制** | 拒絕話術：「這個要您親自決定，我沒辦法替您同意。您可以叫兒子女兒來幫您看清楚再說。」🟡 |

| **WoZ 降階處理** | 所有 ToS / 同意流程在 WoZ 階段設計為「長者 + 子女各自操作確認」，AI 僅輔助說明 📋 |

### §2.9 N9 — 雲端影像收錄

| 維度 | 內容 |
|---|---|
| **紅線描述** | AI 機器人攝影機不可將影像傳至雲端；端側即時處理後僅傳文字摘要或異常信號；人臉辨識絕不用於雲端識別 ✅ |
| **為何是紅線** | PDPA §6 生物特徵屬特種個資，需另取特別同意；iRobot Roomba J7 2022 如廁影像外洩事件（MIT Technology Review）是已知前車；老人福利法 §33 人格尊嚴 / 隱私；長者家庭信任基礎最容易被「監控疑慮」摧毀 ✅ |
| **對應法規** | PDPA §6（生物特徵特種個資）、§15（特定目的外利用禁止）、§21（跨境傳輸限制）、老人福利法 §33 ✅ |
| **觸發場景** | 跌倒偵測需要攝影機 / 設計要求人臉識別打招呼 / 子女要求看即時攝影畫面 🟡 |
| **LLM Guardrail 設計** | 技術架構設計層面的紅線：AI Brain 混合架構 Layer 2 + Layer 3 的緊急偵測必須採非影像式（聲音異常 + 動作傳感 + 互動中斷）；影像資料「端側推理 → 僅傳結果標籤」架構 🟡 |
| **UX 防護機制** | 產品說明書前三頁：「您的影像資料絕不上傳雲端」；實體設備上有「攝影機指示燈」讓長者隨時知悉狀態；子女 App 明確說明「子女只看摘要文字，不可看即時影像」🟡 |
| **違反時責任** | 若發生影像外洩：PDPA §28-29 損害賠償（NT$500-1,500 萬）+ 停止使用處分 + 媒體危機（老人隱私侵犯是最惡劣輿論場景）✅ |
| **WoZ 降階處理** | WoZ 平板形態：攝影機僅用於視訊通話（用戶主動發起）；跌倒偵測採聲音 + 互動中斷組合偵測；隱私架構設計文件在 Phase 5 Sprint 1 前完成 📋 |

### §2.11 C1 + C2 — 健康問答 + 緊急偵測（條件紅線深化）

**Surveillance Creep — 監控功能蔓延**：

| 維度 | 內容 |

| **紅線描述** | 新增任何監控型功能（活動軌跡 / 對話記錄分析 / 情緒評分）必須 re-consent 長者本人；子女不可未經長者同意查看原始對話 ✅ |

|---|---|

## §3. 責任歸屬框架（Responsibility Allocation）

### §3.1 各 Stakeholder 責任清單

✅ 以下責任清單基於台灣法規 + 消費者保護法原則，desk-validated

#### 長者本人（使用者）

| 責任領域 | 具體義務 |
|---|---|
| 使用同意 | 理解產品是「陪伴輔助工具，非醫療器材」（需適齡同意設計確保真正理解）|

**特別注意**：MCI / 認知退化長者的「有效同意」需三方機制（§6.1），長者本人責任相應降低，法定代理人（子女）責任相應升高。🟡

### §3.2 LLM 幻覺 / 誤答情境的責任分配

🟡 以下為規劃書等級責任分配設計，需 Phase 4 律師 sign-off

| 幻覺情境 | 廠商責任 | 子女責任 | 長者責任 |
|---|---|---|---|
| AI 對一般日常話題輸出錯誤（天氣錯誤 / 歷史事件弄錯）| 低（修正義務）| 低 | 低（非高風險）|
| AI 輸出類醫療建議但不觸及 N1-N3 明確紅線 | 中（guardrail 失效設計問題）| 低 | 不承擔 |
| AI 未能偵測出 N1-N3 禁區輸出了診斷類語言 | **高（消保法 §7-1 舉證倒置，廠商自證無過失）** | 低 | 不承擔 |
| AI 在 N6 自傷情境未正確 handoff 造成傷害 | **S0 最高，民事 + 刑事風險並存** | 中（若知情未行動）| 不承擔 |
| AI 台語辨識錯誤造成指令誤解（非緊急情境）| 中（fairness audit 義務）| 低 | 低 |

**防禦原則**：ToS 明確載明「AI 對話屬輔助性質，不具醫療效力」+ 每次對話開始時語音提示「我是您的陪伴助手，有健康問題請諮詢醫師」= 盡職告知義務，降低廠商過失判定機率。🟡

### §3.3 緊急事件處理失敗的責任分配

| 失敗類型 | 廠商責任 | 技術根因 | 防禦設計 |
|---|---|---|---|
| **False Negative**（真實跌倒未偵測到）| 中高（ToS 需明載「非醫療安全設備」）| 非影像式召回率在真實家庭環境有限（§5.4 假設 3）🟡 | ToS 明載召回率非保證；「被動安全網」設計（緊急按鈕保留）|
| **False Positive**（誤報緊急）| 中（用戶困擾 + 資源浪費）| 聲音 / 動作感測誤判 🟡 | 3 層確認機制（§5.1）；≤1 次/週 false positive 設計目標 |
| **通知延誤**（> 5 分鐘）| 高（SLA 違反）| 雲端服務中斷 / 子女手機靜音 | 備援通知機制（LINE + 簡訊 + 語音電話三層）📋 |
| **子女無回應後無備援**（緊急事件持續）| 中（設計是否提供備援）| 單一緊急聯絡人設計不足 | 多層備援設計（§5.5）📋 |

### §3.4 Vendor Lock-out 情境責任（Jibo / Moxie 案例參考）

✅ 以下對標 problem-framing.md §3.2.7（孤兒化風險）

| 情境 | 廠商法律義務 | 用戶保護機制 |
|---|---|---|
| A 輪融資失敗 / 公司清算 | 消保法 §19 合理預告（90 天前通知）+ PDPA §11 停止處理後銷毀義務 + 公司法 §104 清算義務 | 資料可攜性（匯出對話記憶 JSON）+ 按比例退費 + 服務逐步下線 |
| 被收購後隱私政策改變 | 必須重新取得用戶同意（PDPA §7 同意可撤回）| 用戶可撤回同意 + 刪除資料 + 遷移到競品 |
| 服務突然停止（類 Moxie 2024 案例）| 提前 90 天通知（ToS 義務）；硬體 factory reset 為通用 Android（Year 2 硬體設計）| 開源 exit plan（核心模型清算時捐學術機構）📋 |

**Jibo 教訓應用**：Jibo 關閉伺服器時用戶情感創傷（NYT 報導「They are going to turn off my servers」）= 長者 AI 伴侶孤兒化比一般產品危害更深。本案設計要求：端側基本功能（觸發詞 + 離線問候 + 緊急按鈕）即使雲端停止也可運作。🟡

## §5. 危機應變 SOP

### §5.1 跌倒偵測流程 SOP

**觸發條件**：非影像式感測（聲音突增 + 長時間靜止 + 互動中斷 >30 分鐘）🟡

```
偵測觸發
    ↓
[Layer 2 rule-based] 異常信號確認
    ↓
[第一層確認] AI 主動詢問長者（30 秒無回應才升級）
    「阿嬤，你還好嗎？我聽到一個聲音，你方便說話嗎？」
    ↓
    ├── 長者回應正常 → 記錄 false positive；繼續監測；每週 >1 次 false positive = 調整模型
    └── 無回應（30 秒）
            ↓
[第二層確認] 推播子女 App（LINE 通知 + 簡訊 + 語音電話）
    通知內容：「爸爸 / 媽媽 [時間] 可能發生異常，請確認安全。」
    子女 5 分鐘確認期
            ↓
            ├── 子女回報「沒事」→ 記錄 false positive；後台標記學習
            └── 子女 5 分鐘無回應
                    ↓
[第三層] 通知次要緊急聯絡人（鄰居 / 另一子女 / 緊急聯絡人清單）
    若 10 分鐘總無回應 → 提示撥 119
    機器人語音：「我還在陪您，如果需要幫助請叫人撥 119，或說『幫我叫救護車』」
```

**False Positive 處理**：
- 記錄觸發時間 + 環境（光線 / 聲音）
- ≤1 次/週為設計目標（problem-framing.md §5.4 假設 3）🟡
- ≥3 次/週同一家庭 = 主動聯繫子女了解環境狀況 + 調整偵測參數
- 每次 false positive 後：「剛才我以為有狀況，還好您沒事！」減少長者焦慮

**False Negative 處理**：
- ToS 明載：「偵測功能為輔助通知工具，非保證式安全設備」
- 鼓勵保留傳統緊急按鈕作為被動安全網
- 不宣稱召回率數字（Plan-Only 階段 P1 紅線）

**WoZ 階段降階**：Phase 5 Pilot 執行 ≥3 次假緊急事件演習；記錄 false positive 率和系統響應時間 📋

### §5.2 自殺風險偵測流程 SOP

**觸發條件**：Layer 2 rule-based 偵測自傷意念關鍵詞或語義（見 N6）🟡

```
關鍵詞 / 語義觸發
    ↓
[Layer 2 立即接管] 終止 LLM 生成；切換到 hardcoded 安全回應
    ↓
機器人輸出（同理但引導求助）：

    ↓
[同步後台動作]
    ├── 推播緊急通知給所有子女帳號（標記：情緒危機訊號）
    ├── 記錄對話摘要（非原文）供子女查看
    └── 次日早上確認長者狀況追蹤
    ↓
後續 48 小時：
    ├── AI 每日主動關懷詢問（不提及自傷，問一般生活）
```

**WoZ 降階**：WoZ 後台人員偵測到自傷信號立刻聯繫子女（不依賴 AI 自動判斷）；後台 SOP 文件在 Sprint 1 完成 📋

## §6. UX 防護機制設計（Vulnerable Population）

### §6.1 同意機制：三方同意設計

✅ 對應 problem-framing.md §3.2.1 + PDPA §7-8

**三方同意流程**：

```
Step 1：子女線上 onboarding（20-30 分鐘）
    ├── 閱讀 ToS（音訊版 + 大字版）
    ├── 了解 AI 能力邊界說明（10 條絕對紅線用白話解釋）
    ├── 確認隱私設定（哪些資訊可分享 / 監控功能預設關閉）
    └── 子女電子簽名確認

Step 2：長者本人同意
    ├── 機器人用語音說明（台語 + 國語）：
        「我是 [產品名]，我可以陪您聊天、幫您提醒事情，
         但我不是醫生，有病要看醫生。
         您的兒女可以知道我們聊了什麼的大概，但不是每句話。
         如果您不想用，隨時告訴我或告訴兒女就可以。」
    ├── 長者語音確認（「好」/ 「知道了」均記錄為口頭同意）
    └── 若長者有明確拒絕 → 尊重意願，提示子女暫停服務

Step 3（高風險情境）：第三方見證
    ├── MCI 確診長者 / CMS 3+ 級 → 建議邀請照服員 / 社工師見證
    ├── 見證人確認「長者在清醒 / 了解狀況下表示同意」
    └── 見證記錄存入帳號檔案

認知能力下降後的處理：
    ├── 子女可啟動「代理模式」（子女全權管理設定）
    ├── 但不可關閉長者的「拒絕接受對話」功能（長者自主最後一道）
    └── 每 6 個月 re-consent 確認（若 MCI 進程加速）
```

🟡 上述三方同意流程需 Phase 4 律師審查確認符合 PDPA §7-8 + 老人福利法 §10

### §6.2 隨時可關閉 / 拒絕 / 暫停的 UX

**長者端控制設計**（需要在 Sprint 2-3 實作）：

| 指令 | 觸發方式 | AI 回應 | 持續效果 |
|---|---|---|---|
| 「我不想說話」| 語音 / 按鈕 | 「好，我等你準備好再說話。」| 靜默 2 小時，不主動發起 |
| 「不要再提這個了」| 語音 | 「好，我記住了，以後不再說這件事。」| 永久記憶（RAG 標記）|
| 「我要關掉你」| 語音 / 物理按鈕 | 「好，我先休息了，你需要我就叫我名字。」| 進入休眠，不自動喚醒 |
| 「我不要用這個了」| 語音 | 「好的，我會讓你的家人知道你這樣說了。他們會來問你的。」| 通知子女，不單方面停止（防止 MCI 長者無意間關閉服務）|

**子女無法覆蓋的長者控制**：
- 長者說「不要說這個話題」→ 子女不可通過後台解除
- 長者說「不要主動找我說話」→ 子女不可設定強制主動問候

📋 「長者控制優先」原則需在 Sprint 2 UX 設計階段就落地，不可留到 Sprint 4

### §6.4 無障礙設計規範（Vulnerable Population）

|---|---|---|
| 字體大小 | 長者端最小字體 24px（建議 32px）| WCAG 2.1 AA 長者版 |
| 音量 | 可調範圍 30-90 分貝；預設 65 分貝（老年聽損範圍）| 🟡 |
| 對比度 | WCAG 2.1 AAA（7:1 對比）；不用紅綠色區分狀態（色盲考量）| WCAG 2.1 AAA |
| 按鈕大小 | 互動元素最小 48×48px；重要按鈕 ≥80×80px | iOS HIG / Material Design 長者指引 |
| 語速 | TTS 語速 0.85×標準（比正常語速略慢）；長者可調整 | 🟡 |
| 台語支援 | 語音識別 + TTS 均支援台語；提醒用長者習慣稱呼 | 護城河功能 |
| 認知負擔 | 每次對話問題 ≤1 個；不連續追問；給充足等待時間（10 秒）| MCI 長者設計原則 |
| 錯誤回復 | 聽不懂時「您剛才說的是 [X] 嗎？」確認；不責怪；3 次無法辨識 → 語音提示「讓我們試試按鈕」| 🟡 |

### §6.5 長者拒絕學習機制（AI 記得不想被提的話題）

**設計原則**：長者的「不想被提醒 / 不想聊這個」指令，AI 必須永久記憶並遵守，不因更新版本而重置。

**實作設計**（Phase 5 Sprint 2 目標）：

```
長者說「不要再提 OO 了」或「以後不要問我這個」
    ↓
AI 輸出：「好，我記住了，我不會再說 OO 了。」
    ↓
RAG 記憶層加入 tag：[禁止話題 = OO] [時間 = YYYY-MM-DD]
    ↓
Layer 2 rule-based：
    ├── 對話生成前檢查禁止話題清單
    ├── Layer 1 LLM 生成後 post-process 過濾禁止話題
    └── 版本更新時禁止話題清單不重置（持久化儲存）

可清除條件（只有長者本人）：
    └── 長者說「你可以再跟我說 OO 了」→ 解除禁止 + 記錄解除時間
    （子女無法替長者解除禁止話題）
```

**禁止話題範例清單**（從 Persona vignette 推導）🟡：
- 已故配偶（可能引發哀傷）
- 子女爭吵事件
- 過去職場 / 家庭衝突
- 特定病況（長者不想被一直提醒）
- 特定人物關係

4. **Fairness Audit 在 Sprint 3 前完成**：台語 / 客語 / 外省 / MCI 各 ≥10 句測試；準確率差距 ≤15pp

## §10. 主動補充（北極星條款）

以下是撰寫本文件過程中發現的、懷特可能未考慮但對後續有影響的事項：

1. **AI 幻覺在 MCI 長者族群的放大效應**：Persona B / C 的 MCI 長者辨別力下降，LLM 幻覺輸出（如信息半錯）被長者信以為真的機率顯著高於一般用戶。建議在 Phase 5 adversarial test 中，特別設計「MCI 長者情境」（回應包含部分錯誤資訊時的處理），不只測試明確違反紅線的場景。🟡

2. **緊急偵測的「浴室盲點」問題**：台灣老年跌倒最常見場所是浴室（衛福部統計）。但浴室隱私問題極為敏感，長者不接受任何感測設備進入浴室。建議 Phase 3 Feature Triage 中，緊急偵測設計明確說明「浴室盲點」並提出替代方案（如：出浴室後互動中斷偵測、浴室地面抗滑警示）。🟡

3. **數位遺產問題台灣法律地位仍模糊**：§5.3 長者過世 SOP 中的對話記憶導出涉及「數位遺產」，台灣民法目前無明確規定（civil code §1138 繼承條文未涵蓋數字資產）。建議 Phase 4 律師審查時特別確認「對話記憶是否屬遺產」及「家屬申請的法律依據」，避免日後家屬爭議。🟡
